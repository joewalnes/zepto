================================================================================

ID:       QA-SEC-012
NAME:     ReDoS protection covers regex MATCH time, not just compilation (REGRESSION)
PRIORITY: P1
FEATURE:  sec regex
RELATED:  bugs.md P1 "FindEngine.pm ReDoS timeout only covers regex
          compilation, not matching"; QA-SEC-005 (the original, narrower
          compile-time-only protection)

SETUP
  A file whose only content is 28 "a" characters (no trailing char that
  would let the regex bail out early).

STEPS
  1. ⌃F, ⌃R to enable regex mode.
  2. Type the pattern `(a?){28}a{28}` — a counted-repetition-of-optional
     form that causes genuine catastrophic backtracking in Perl's own
     regex engine (Perl auto-optimizes away the textbook `(a+)+$` demo,
     so that one does NOT reproduce this bug — this pattern does,
     verified to take 15+ seconds of pure backtracking unguarded).

VERIFY
  - Editor does not hang — search returns/aborts within ~1-2 seconds
    (MATCH_ALARM_SECS), not 15+.
  - Editor remains fully responsive to further input afterward (Escape,
    typing, ⌃Q all still work).
  - No crash; process is still alive throughout.
  - This is distinct from QA-SEC-005: that test's pattern only ever
    exercised the compile-time alarm (compilation of `(a+)+$` is
    instant regardless of catastrophic-backtracking risk at match
    time) — it did not actually prove match-time protection existed.
    This test's pattern is chosen specifically because it stays cheap
    to *compile* but expensive to *match*.

ID:       QA-SEC-013
NAME:     AI completion API key never appears in curl argv (REGRESSION)
PRIORITY: P2
FEATURE:  sec ai-completion
RELATED:  bugs.md P2 "AI API key passed as a curl command-line argument,
          visible to other local users via ps"; QA-REG-209

SETUP
  AI Completion configured (via "AI Completion: Setup") against a local
  test HTTP endpoint that deliberately delays its response, so the real
  curl child process stays alive long enough to observe.

STEPS
  1. Type in the editor to trigger a real AI completion request.
  2. While the request is in flight, inspect `ps aux` (or
     `/proc/<pid>/cmdline` on Linux) for the curl child process.

VERIFY
  - curl is invoked with `-K <temp-file>` (a config file), never with
    `-H "Authorization: Bearer ..."` in argv.
  - The raw API key does not appear anywhere in `ps aux` output at any
    point during the request.
  - The word "Authorization" does not appear anywhere in `ps aux`
    output either (confirms the header text itself isn't in argv, not
    just that the specific key string happens not to match).
  - The temp config file is mode 0600 and is deleted after the request
    completes (or is cancelled — AI requests are routinely cancelled by
    the very next keystroke).
  - The request still succeeds: the configured endpoint receives the
    correct `Authorization: Bearer <key>` header (via the config file,
    not argv), proving this isn't just "the feature stopped working".
  - Automated via `qa/scripts/tier1/reg_209_ai_apikey_not_in_ps.sh`.

ID:       QA-SEC-014
NAME:     AI Completion setup rejects a non-https API URL (REGRESSION)
PRIORITY: P3
FEATURE:  sec ai-completion
RELATED:  bugs.md P3 "AI API URL has no scheme enforcement, allowing
          silent plaintext transmission of the API key"; QA-REG-210

SETUP
  None — fresh "AI Completion: Setup" flow from the command palette.

STEPS
  1. ⌃Space, run "AI Completion: Setup".
  2. At the "API URL:" prompt, enter an `http://` URL (or any URL with
     no `https://` prefix) and press Enter.

VERIFY
  - A clear error message is shown (mentions https / plaintext risk),
    not silent acceptance.
  - The wizard does NOT advance to the "Model:" step.
  - The rejected URL is never written to preferences.json.
  - Re-running setup with a well-formed `https://` URL proceeds through
    all three steps (URL, Model, API Key) normally and is saved.
  - Automated via `qa/scripts/tier1/reg_210_ai_url_https_required.sh`.

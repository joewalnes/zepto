ID:       QA-MD-009
NAME:     Dim emphasis delimiters
PRIORITY: P3
FEATURE:  md emphasis
RELATED:  bugs.md P3 "Dim Markdown formatting delimiters" (FIXED),
          QA-REG-135, QA-SYN-015

SETUP
  Markdown file with:
    This is **bold text** and this is *italic text*.
    This is ***bold and italic*** combined.
    This is ~~strikethrough text~~ here.
    This is ==highlighted text== here.

STEPS
  1. Observe the line in both dark and light themes (⌃T toggles).

VERIFY
  - The `**`, `*`, `***`, `~~`, `==` delimiter characters render in a
    faint/low-contrast color, distinctly dimmer than both the plain
    body text and the styled content they surround.
  - The styled content itself (bold/italic/bold-italic/strikethrough/
    highlighted text) keeps its normal, prominent styling — the
    delimiters are dim, not the content.
  - No characters are hidden — the `**`/`*`/`~~`/`==` marks are still
    visible on screen, just visually de-emphasized (color only, not
    concealment).
  - Other punctuation (heading `#`, list `-`/`1.`, blockquote `>`,
    code fences, link `[]()` brackets, `---`/`***` thematic breaks) is
    UNCHANGED — still the normal punctuation color, not dimmed.
  - Non-Markdown files are unaffected (e.g. Perl `2 ** 3` keeps the
    normal operator color).

NOTES
  Deterministic coverage (token type + exact theme RGB, both themes):
  tests/syntax_rendering.t subtests "Markdown emphasis delimiters use a
  dedicated dim token type", "Theme defines faint colors for
  formatting_delim in both themes", "Rendered markdown shows dimmed
  delimiter distinct from bold content", "Non-Markdown languages are
  unaffected by formatting_delim". Sample fixture:
  tests/samples/markdown_complete.{md,expected}.

ID:       QA-MD-011
NAME:     Inline images
PRIORITY: P3
FEATURE:  md image
RELATED:  QA-MD-012, QA-TERM-014

STEPS
  1. Open a `.md` file containing `![alt](relative/path.png)` in a
     Kitty-graphics-capable terminal (Ghostty, Kitty, WezTerm, or any
     `TERM`/`TERM_PROGRAM` matched by
     `Zepto::Terminal->supports_kitty_graphics()`).

VERIFY
  - The image renders inline via the Kitty graphics protocol, reserving
    blank "spacer" rows in the text area sized to the image's aspect
    ratio (`Renderer::_detect_markdown_images` /
    `_render_text_area`'s `image_spacer` entries).
  - Non-Kitty terminals and non-Markdown files are unaffected — the
    literal `![alt](path)` text renders as plain Markdown syntax.

NOTES
  This entry previously said "future / not yet implemented" — stale;
  corrected 2026-08-30 while investigating QA-REG-175 (found the feature
  is fully implemented, just untested by this file until now). The
  original P3 "Inline image rendering" bugs.md entry it referenced was
  already SKIPPED as superseded, not a live blocker.

ID:       QA-MD-012
NAME:     Inline-image spacer rows use the real theme background
          (REGRESSION)
PRIORITY: P2
FEATURE:  md image background-fill
RELATED:  QA-MD-011, QA-REG-175
SCRIPT:   tier1/reg_175_image_spacer_bg.sh

STEPS
  1. Open a `.md` file with an inline image (see QA-MD-011) in a
     Kitty-graphics-capable terminal.
  2. Inspect the raw ANSI bytes for the blank spacer rows reserved below
     the image (e.g. via `tmux capture-pane -e`).

VERIFY
  - The spacer rows' text-area cells carry the current theme's real `bg`
    color, in both dark and light theme.
  - Regression guard for a bug where the spacer-row fill read a
    nonexistent `editor_bg` theme role (only `bg` exists) — silently
    emitted no color of its own and showed the preceding gutter fill's
    color bleeding through instead, in both themes. Found via code audit
    while investigating QA-REG-174 (see bugs.md 2026-08-30 "Light-theme
    dark background fill investigation").

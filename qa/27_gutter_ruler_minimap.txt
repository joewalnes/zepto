ID:       QA-GUT-020
NAME:     Minimap auto-hides below MINIMAP_MIN_COLS, independent of the
          manual toggle (REGRESSION)
PRIORITY: P1
FEATURE:  minimap layout narrow-width
RELATED:  bugs.md 2026-08-30 "Minimap eats scarce width at narrow
          terminal sizes" — QA-REG-177

STEPS
  1. Open a file long enough to trigger the minimap (more lines than fit
     the viewport) with the Minimap preference ON (default).
  2. At a wide terminal (80 cols or more), confirm the minimap column
     (Braille density pattern) is visible on the right edge.
  3. Resize/relaunch at exactly 60 cols. Confirm the minimap is still
     visible.
  4. Resize/relaunch at 59 cols. Confirm the minimap has disappeared —
     the reclaimed column goes to document text, not dead space.
  5. Resize/relaunch at 40 cols (with a realistic ~15-20 char filename,
     file tree closed). Confirm no minimap and the status bar renders
     cleanly with no glitch or layout jump.
  6. At 80 cols, toggle Minimap off via the command palette or ⌥M.
     Confirm it hides. Toggle back on. Confirm it reappears. (The manual
     toggle is unrelated to this auto-hide behavior and must keep
     working normally above the threshold.)

VERIFY
  - Minimap present at cols >= 60 (MINIMAP_MIN_COLS), given otherwise
    sufficient room and preference ON.
  - Minimap absent at cols < 60, even though the older per-frame
    MIN_TEXT_WIDTH check alone would have left it enough room to render
    (e.g. at 40 cols, tentative_text ~= 27 >= MIN_TEXT_WIDTH — the bug
    was that this dynamic check was the ONLY gate; there was no hard
    floor for a "is a minimap even worth it here" threshold).
  - No visual glitch or layout jump exactly at the threshold — the
    reclaimed column width goes straight to document text.
  - Manual Minimap toggle (⌥M / command palette) still works normally
    at widths at/above the threshold — this fix does not touch that
    preference or turn it into a new user-facing toggle.
  - See tests/renderer.t "get_minimap_width returns 0 below
    MINIMAP_MIN_COLS even with plenty of room", "Minimap auto-hides via
    full render at narrow widths (QA-REG-177)", "Manual minimap
    preference still works normally above MINIMAP_MIN_COLS
    (QA-REG-177)" for the automated regression coverage.

ID:       QA-GUT-021
NAME:     Minimap VCS-status coloring stays correct on a large file
          (subsampled aggregation, REGRESSION)
PRIORITY: P3
FEATURE:  minimap VCS status
RELATED:  bugs.md P3 "Minimap VCS-status aggregation scans the whole
          document on every keystroke" — QA-REG-233

STEPS
  1. Open a git-tracked file large enough to span many minimap rows
     (thousands of lines) with a handful of scattered added/modified
     lines relative to HEAD.
  2. Confirm the minimap (Braille density column) is visible.
  3. Go to a known-changed line (⌃G). Confirm the gutter shows a VCS
     change marker on that line, and the line's content matches the
     expected change.
  4. Type a short burst of characters. Confirm the edit appears
     immediately with no visible freeze/stutter, and the minimap remains
     rendered (no garbling, no crash).

VERIFY
  - Minimap VCS-status coloring for a row still reflects a real change in
    that row's line span after the fix that added `MAX_VCS_SAMPLE_LINES`
    subsampling — a row's span below the 200-line cap is checked exactly
    (same as before the fix); a span above the cap samples 200 evenly
    spaced lines, which is guaranteed to catch any contiguous changed
    hunk of `ceil(line_span / 199)` lines or more (real diffs are
    hunk-based, not scattered isolated single lines).
  - Typing on a large git-tracked file does not visibly stutter or hang
    (coarse smoke check — the real timing evidence is in
    tests/minimap_vcs_perf.t, not this interactive script; PTY/tmux
    round-trip overhead is too coarse to discriminate millisecond-level
    render differences).
  - Known accepted limitation, not verified here as a pass/fail (see
    tests/minimap_vcs_perf.t's "KNOWN LIMITATION" subtest instead): a
    truly isolated single-line change that doesn't land on a sampled
    line, in a row spanning more than 200 lines, can be missed by the
    minimap's VCS coloring. This is the same class of tradeoff the
    pre-existing braille `MAX_SAMPLE_LINES` cap already accepts for text
    density.
  - See `qa/scripts/tier1/reg_233_minimap_vcs_perf.sh`.

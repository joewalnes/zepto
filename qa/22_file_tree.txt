ID:       QA-TREE-002
NAME:     ⌃B toggles focus when tree visible
PRIORITY: P1
FEATURE:  tree focus

STEPS
  1. Tree visible. Editor focused (e.g. after opening a file from the
     tree, which unfocuses it but leaves it open — see QA-REG-220).
  2. Press ⌃B.

VERIFY
  - Focus moves to tree (refocuses it — it does NOT re-hide the tree from
    this state; see QA-REG-220, the fix for bugs.md's P2 "⌃B hides the
    tree instead of refocusing it when visible-but-unfocused").
  - Status bar shows tree-context pills (not document pills).
  - Press ⌃B again (now tree-focused): tree hides entirely, editor uses
    full width — confirmed via direct `hangon` interactive testing
    2026-08-31 while fixing QA-REG-220, matching QA-TREE-001 and
    `cmd_toggle_tree`'s current code (`Editor.pm`). This is the confirmed
    current behavior for the "Confirm which is current" question below.

NOTES
  This entry previously carried an unresolved note ("Confirm which is
  current") about whether ⌃B-while-focused hides the tree or only
  unfocuses it — `qa/scripts/tier1/reg_183_tree_back_hint.sh` and
  QA-TREE-020 below both describe/assert the latter, but reg_183's
  "Tree panel remains open after ⌃B" check is tautological (it greps for
  the currently-open file's name, which is always present via the tab bar
  regardless of whether the tree panel itself is visible) and has been
  giving a false pass for the "stays open" claim rather than actually
  verifying it. Confirmed directly via `hangon` (2026-08-31, QA-REG-220
  fix session) that the real, current behavior hides the tree on the
  second press, matching QA-TREE-001. Not changing the "hides" behavior
  itself — only the VU (visible-but-unfocused) → refocus case was an
  actual bug (QA-REG-220). Logged the reg_183/QA-TREE-020 stale-text and
  tautological-assertion mismatch in bugs.md; not fixed there (out of
  scope for this session).

ID:       QA-TREE-013
NAME:     Tree filter via typing / to filter
PRIORITY: P1
FEATURE:  tree filter
RELATED:  bugs.md P1 "File-tree flat-filter search... has zero UI
          trigger" (FIXED, QA-REG-216) — this feature was fully built and
          unit-tested underneath but completely unreachable from the
          running editor until that fix wired '/' up as the trigger.
          qa/scripts/tier1/tree_013_filter.sh

SETUP
  Tree focused.

STEPS
  1. Without pressing `/`, type a few plain letters.
  2. Press `/`.
  3. Type a query matching one file but not others (e.g. "edit").
  4. Press Backspace enough times to empty the query.
  5. Press Escape once, then Escape again.

VERIFY
  - Step 1: plain typing with no `/` trigger does NOT filter — the tree
    stays in normal browse mode (this is the exact bug the fix above
    addresses: confirms the old broken "nothing happens" state hasn't
    silently come back in a different form).
  - Step 2: the status bar's tree-context hint row swaps its `/ filter`
    pill to `Esc clear`, and the search bar (search icon + query, always
    row 1 of the tree panel) becomes visible with the cursor positioned
    in it.
  - Step 3: tree switches to a flat filter list — only matching files are
    shown, with matched characters highlighted; non-matching files (and
    all directories) drop out of the list entirely.
  - Step 4: as the query shrinks back to empty, the full hierarchical
    tree reappears (filter mode stays active with an empty query — see
    QA-TREE-005's script for that specific edge case).
  - Step 5: the first Escape clears the filter but the tree stays
    focused (hint row reverts to `/ filter`); the second Escape unfocuses
    the tree back to the editor, matching Esc's normal-mode behavior.
  - See QA-TREE-030 for Enter opening the highlighted filtered result.

ID:       QA-TREE-027
NAME:     Failed preview shows an error message instead of silence
PRIORITY: P2
FEATURE:  tree preview
RELATED:  QA-REG-154, QA-TREE-002, QA-TREE-024, QA-TREE-025

STEPS
  1. Open a directory containing a readable file. Open tree (⌃B).
  2. Arrow onto the file — preview shows its content.
  3. Outside zepto, revoke read permission on that file
     (`chmod 000 <file>`), simulating permissions changing or the
     file becoming unavailable after the tree scanned it.
  4. Arrow off the file, then back onto it, to trigger a fresh
     preview attempt.

VERIFY
  - Status bar shows an error message, e.g.
    "Preview failed: Cannot open <path>: Permission denied" —
    not silence.
  - Editor does not crash; no Perl stack trace on screen.
  - The broken-preview attempt doesn't leave a stuck tab or stale
    tree state: switching to a different, readable file previews it
    normally right after.
  - Arrowing rapidly past several broken files does not stack
    messages or leave multiple broken preview tabs open — each
    failed attempt cleanly reverts to the pre-preview tab before the
    next attempt starts, and the message is replaced (not appended)
    by the next action, per the status-bar "persist until replaced"
    convention (docs/UI_GUIDELINES.md).

NOTES
  The file tree only lists files that pass `-r` at scan time
  (FileTree::_scan_dir_one_level), so a file that is already
  unreadable when the tree scans never appears in the listing at
  all — you cannot navigate to it. The realistic way this fires is
  a TOCTOU race: readable at scan time, unreadable by the time the
  user previews it (step 3 above). Root cause and fix: bugs.md P3
  "Silent eval swallow in file-tree preview open" (FIXED).

ID:       QA-TREE-028
NAME:     ⌃B back-to-editor hint is discoverable from the tree itself (REGRESSION)
PRIORITY: P1
FEATURE:  tree discoverability
RELATED:  bugs.md P1 "FILE_TREE-context discoverability" (QA-REG-183/184/185),
          docs/UI_GUIDELINES.md "Discoverability Contract"

STEPS
  1. Open zepto with a project directory, focus tree (⌃B).
  2. Look at the tree's status bar hint row — do not consult docs/help.

VERIFY
  - Without reading any documentation, a first-time user can see how to
    get back to editing: a `⌃B back` pill is visible in the hint row.
  - Pressing ⌃B returns focus to the editor; the tree panel stays open
    (this is a focus switch, not a dismiss — contrast with `Esc`, which
    closes the tree per docs/UI_GUIDELINES.md "Navigation And Focus").
  - At narrow widths (~60 cols), `⌃B back` is still visible even after
    other tree-specific pills (`↵ open`, `↑↓`, `←→ fold`) have dropped —
    it has the highest priority of the tree-context pills.
  - At extreme widths (~40 cols), if `⌃B back` doesn't fit, the row
    degrades to blank fill (not garbled glyphs) and `⌃␣ Commands` (the
    universal fallback signpost) is still visible — a user can always
    find "the place that has all shortcuts" even here.
  - When there's enough room (~100+ cols), the same close-tab/switch-tabs/
    quit hint DOCUMENT context's tab bar shows also appears in the tree's
    hint row, in identical wording.

ID:       QA-TREE-029
NAME:     Tree status bar breadcrumb never overflows the terminal width (REGRESSION)
PRIORITY: P1
FEATURE:  tree discoverability
RELATED:  bugs.md P1 "FILE_TREE-context breadcrumb path can overflow the
          terminal width, corrupting the screen" (QA-REG-186)

STEPS
  1. Open zepto on a directory containing an entry with a realistic-length
     name (even something short like ".claude" reproduces this).
  2. Resize the terminal to 40x15 with the tree focused.

VERIFY
  - The status bar row never wraps onto a second terminal row — the tab
    bar (the screen's first row) stays visible, not scrolled off the top.
  - The breadcrumb path shortens with a leading ellipsis ("…") when there
    isn't room for it in full, keeping the file/folder's own name (the
    tail of the path) visible rather than the front of the path.
  - `Open ⌃O` and `Commands ⌃␣` remain visible and functional throughout.
  - At a wide enough terminal (~100+ cols), the full un-ellipsized path
    renders normally.

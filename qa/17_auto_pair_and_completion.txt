ID:       QA-CPLT-021
NAME:     Word completion scans ALL open buffers, not just the active one
PRIORITY: P1
FEATURE:  completion cross-buffer
RELATED:  bugs.md P2 "Buffer word completion" (ALREADY IMPLEMENTED)

SETUP
  Two tabs open: tab A contains a long, distinctive identifier that
  appears nowhere else (e.g. `longUniqueVariableNameXYZ`); tab B is
  empty/unrelated.

STEPS
  1. Switch to tab B (⌥. or ⌥,).
  2. Type a 2+ char prefix of the identifier from tab A (e.g.
     `longUnique`).
  3. Press Tab to accept.

VERIFY
  - Ghost text suggests the completion even though the full word has
    never been typed in tab B — it comes from CrossBufferWordProvider
    scanning tab A.
  - Accepting inserts the full identifier from tab A into tab B.

NOTES
  `lib/Zepto/Completion/CrossBufferWordProvider.pm` is a superset of a
  same-buffer word provider: it scans every open tab's document (cached
  per-document by content_version, rebuilt only when something
  changed), with a proximity score bonus for words from the currently
  active document. This is what makes the "Buffer word completion"
  bugs.md entry ALREADY IMPLEMENTED rather than a gap to fill — it
  covers cross-buffer, which the original ask didn't even require.
  QA-CPLT-009 already covers same-buffer triggering; this test is the
  one that actually exercises the cross-tab path.

ID:       QA-CPLT-022
NAME:     Completion never offers a self-referential suggestion that just
          reconstructs the word's own already-present tail (REGRESSION)
PRIORITY: P2
FEATURE:  completion word self-match
RELATED:  bugs.md P2 "Stale duplicated tail on the cursor's own line
          after typing into a large file" (fixed 2026-08-30);
          QA-REG-165

STEPS
  1. Open a large file where a line reads e.g. `row2000text` and jump
     the cursor to the very front of that line (before the `r`).
  2. Type 2+ characters, e.g. `a`, then `b` (matching the completion
     min-trigger length), with a real pause between keystrokes so the
     debounced completion trigger fires between them, same as a human
     typing.

VERIFY
  - Screen shows exactly `abrow2000text` — no duplicated ghost-text
    copy of `row2000text` appended after it.
  - Waiting past the completion debounce window (~1-2s) does not cause
    a duplicate to appear later either.
  - Typing further characters into the same word never produces a
    duplicate, at any position in the file (start, middle, end).
  - A genuinely DIFFERENT completion candidate elsewhere in the buffer
    that happens to share the same prefix still ghost-completes
    normally — only self-referential candidates (whose suggested
    suffix would just reconstruct text already sitting after the
    cursor) are rejected.

NOTES
  Root cause was in `Completion::Controller::trigger()`, not rendering:
  CrossBufferWordProvider rescans the active document on every
  keystroke, so typing at the front of an existing word makes the
  scanner "discover" the word-so-far as a completion candidate for its
  own prefix. Its suggested suffix is then just the text already
  sitting after the cursor, and ghost-text rendering paints it right
  after the real content, producing an on-screen-only duplicate (the
  saved document was always correct). See `qa/scripts/tier1/
  reg_165_ghost_completion_self_match_render.sh` for the executable
  regression coverage — it asserts ON-SCREEN content directly, since
  this bug never touched the document.

ID:       QA-CPLT-023
NAME:     Escape-dismiss of ghost text, then a delayed burst starting with
          a space, does not drop or corrupt the leading character
PRIORITY: P1
FEATURE:  completion, input parsing
CROSS-REF: QA-REG-170 (bugs.md P2 "Escape immediately followed by a burst
           keystroke send can drop or corrupt the next character(s)")

SETUP
  A word that will trigger ghost-text completion (2+ char prefix
  matching an existing word elsewhere in the document).

STEPS
  1. Type a prefix that produces an active ghost-text suggestion.
  2. Press Escape to dismiss it.
  3. Wait somewhere between ~0.1s and ~1s (any gap under the full
     idle-read timeout but long enough that the Escape and the next
     keystroke arrive in genuinely separate reads).
  4. Type a burst of text whose first character is a space (e.g.
     " moreWords").

VERIFY
  - The leading space is preserved — the new text is NOT glued
    directly onto the previously-typed word with no separator.
  - No spurious newline appears in place of the space.

NOTES
  Root cause: InputParser only resolved a lone ESC via the ~0.5s
  idle-timeout flush. If the next byte arrived in a separate read
  before that full timeout elapsed, it got appended to the pending
  ESC and reparsed as a continuation — and since space (0x20) is in
  the Alt-key byte range (32-126), "ESC" + later space fused into
  "Alt+Space", which has no handler, silently dropping the space.
  Fixed by adding ESC_DISAMBIGUATION_TIMEOUT (30ms) in InputParser.pm:
  a lone ESC older than that is resolved as a standalone Escape key
  before any newly-arrived bytes are treated as its continuation. Not
  actually specific to completion-dismissal — any Escape followed by a
  32-126 byte in a separate read within the old ~0.5s window triggered
  it; ghost-text dismissal was just the discovery scenario.

ID:       QA-SYN-023
NAME:     Incremental re-highlighting stays correct after an edit that
          changes a downstream line's starting state (token cache)
PRIORITY: P2
FEATURE:  syntax cache incremental
RELATED:  bugs.md P2 "Syntax highlighter re-tokenizes every visible line
          on every render — no token cache"; QA-REG-199, QA-REG-200
          (qa/40_regression_bugs.txt)

STEPS
  1. Open a JS file with a plain code line, followed later by an
     ordinary "boundary" line, followed by more plain code.
  2. Edit the boundary line so it opens an unclosed `/* block comment`.
  3. Observe the lines below it (never directly edited).
  4. Undo the edit.
  5. Observe the same lines again.

VERIFY
  - After step 2: the untouched lines below the boundary render in the
    comment color (not their original keyword/string colors) — the
    highlighter re-tokenizes them using the NEW state carried down from
    the edited line, not stale cached tokens from before the edit.
  - Everything after the boundary line stays comment-colored until an
    actual `*/` closes it (verified by adding one mid-line further down
    and confirming normal coloring resumes on the rest of that line).
  - After step 4 (undo): those same lines revert to their original
    coloring — not stuck showing the mid-edit comment coloring.
  - Discoverable: this is passive, automatic behavior with no separate
    command — any syntax-highlighted file re-highlights live as you type,
    matching how highlighting already behaves everywhere else in the UI.
  - Automated as `qa/scripts/tier1/reg_199_highlighter_cache_upstream_edit.sh`
    and `qa/scripts/tier1/reg_200_highlighter_cache_undo_restores_tokens.sh`,
    which check the actual rendered ANSI color codes rather than just
    screen text (text is identical either way — only the color changes).

ID:       QA-SYN-024
NAME:     A grammar's tokenize() call cannot hang the editor — bounded by
          a per-line timeout guard, ordinary highlighting unaffected
PRIORITY: P3
FEATURE:  syntax highlighter regex timeout guard
RELATED:  bugs.md P3 "No regex-match timeout in the syntax-highlighting
          path" (structural gap, no exploit found in any of the ~53
          shipped grammars — see writeup); QA-REG-233
          (qa/40_regression_bugs.txt); QA-SEC-012 (FindEngine.pm's
          equivalent match-time alarm for Find, which this mirrors).

STEPS
  1. Open any syntax-highlighted file (e.g. a `.pl` file with keywords,
     strings, comments, numbers).
  2. Observe it renders promptly with full coloring.
  3. Edit the file (add/remove lines, type at various positions).
  4. Observe highlighting keeps up, with no perceptible lag or freeze.

VERIFY
  - Highlighting renders correctly and promptly — no regression from the
    timeout guard added around `Highlighter.pm::tokenize_line()`'s call
    into each grammar's `tokenize()`.
  - No user-facing command or setting is needed — this is a passive
    safety net, not a feature with its own UI surface, so there is
    nothing new to discover in the command palette or status bar (same
    reasoning as `FindEngine.pm`'s equivalent match-time alarm, which
    also has no dedicated UI control).
  - Discoverable indirectly: if a grammar ever does hit the timeout, the
    affected line falls back to plain/unhighlighted text rather than
    freezing the editor — a visible (if degraded) result, never a hang.
  - Automated as `qa/scripts/tier1/reg_233_highlighter_timeout_guard.sh`
    (drives the real running editor: opens a highlighted file, confirms
    content renders, and confirms a typed edit is accepted and rendered
    within a 3-second budget). The actual guard-fires-on-a-pathological-
    regex mechanism (no real shipped grammar is known to trigger it) is
    proven at the unit level by `tests/highlighter_regex_timeout.t`,
    using a synthetic test-only grammar and a fork+watchdog hang check
    against the pre-fix code (confirmed hung 31.7s unfixed, bounded to
    ~0.25s fixed) — see bugs.md for the full writeup.

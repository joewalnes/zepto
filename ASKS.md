## 0. [DONE — 2026-09-01, `f9ec822` on `main`] Cursor can end up outside valid line numbers after paste → undo → move/redo

Reported live, exact repro not initially pinned down by the user: *"I pasted a block of text, then hit undo, then some sequence of moving / redo, and my cursor ended up outside of the valid line numbers. I'm not sure exactly how I did it."* P0 per this project's severity scale.

**Found and fixed.** A systematic fuzz sweep (23,880 paste/undo/redo/move permutations) found the minimal trigger was simpler than reported: **paste a multi-line block, press undo once** — no movement or redo needed. Root cause: `Zepto::Document::undo()`/`redo()` only replay buffer mutations and never touch the view's cursor position; `cmd_undo`/`cmd_redo` in `Editor/Commands.pm` called them and left the cursor wherever it was, which can be past the document's new (shrunk) line count. `View::set_cursor()` already clamped correctly, but undo/redo never routed through it. Symptom confirmed interactively: status bar showed `6:1` on a 3-line document, and the next typed keystroke silently landed on the actual last line (`line_col_to_offset()` saturates) rather than the line the UI displayed — a real, silent-corruption-class bug, not cosmetic.

**Fix:** new `View::clamp_to_document()` re-clamps cursor, selection anchor, all multi-cursors and their anchors, and scroll position into current bounds; `cmd_undo`/`cmd_redo` (the only two callers of `Document::undo`/`redo`) call it. Proven unrelated to this session's own `Document.pm` undo-group/`_content_version` changes (QA-REG-226/227/228) — the fuzz sweep fails identically on the commit immediately before those landed, and `git log -L`/`git show --stat` confirm neither touched `cmd_undo`/`cmd_redo` or this code path.

**Not resolved, left as an open design question (not blocking):** after undo, the cursor lands wherever it gets clamped to (e.g. the last line), not restored to its pre-edit position the way most editors do — that would require `Document` to start recording cursor position in undo entries, a more invasive, user-visible behavior change to every undo/redo. Deliberately left as a future decision rather than picked unilaterally. See `bugs.md`'s full writeup for QA-REG-230 and the fuzz-sweep evidence.

## 2. [DONE — 2026-09-01, `353b54f` on `main`, pushed] Sticky/goal column for cursor movement

**Investigated, found already correctly implemented — no code change needed.** Reported live: "As I move cursor down across lines (either via mouse drag or arrows), the column indicator on top ruler jumps around due to lines ending before cursor position."

Design, confirmed by the user 2026-09-01 (kept below for the record — turned out to already match reality):
- Track a separate "goal column" that survives moving through shorter lines (standard "sticky column" pattern).
- Show the cursor pinned at true end-of-line when goal > line length, rather than drawing past the text.
- End key sets goal = actual line end.
- Typing past-end: **snap to true end-of-line** (user's explicit decision — "snap to true end of line on type") — do not implement whitespace-padding, that option is rejected.

**What was found:** `View.pm`'s `_preferred_col` field already implements exactly this — horizontal movement (and any explicit `set_cursor()` repositioning) resets it, vertical movement (arrows, Page Up/Down, word-wrap-aware) leaves it untouched and clamps only the visible `cursor_col`, and typing always inserts at the true (clamped) position with no padding. Independently re-verified by the foreman via a fresh `hangon` session (not just trusting the worker's report) — arrow-key sticky-column restoration and snap-not-pad both confirmed working exactly as designed. No `View.pm`/`Editor.pm` changes were made; the branch added 11 new regression-guard subtests (previously only one pre-existing test partially covered this) plus a QA script (`QA-NAV-019`), all mutation-tested to confirm they actually bite.

**One nuance for the record, not a further action item:** the "via mouse drag" half of the original report has a real explanation that's *not* a bug — mouse-drag recomputes the cursor column fresh from the live pointer position on every drag-move event (via `set_cursor()`, same call every keyboard reposition uses), so it has no persistent goal column at all. A real mouse drag is essentially never perfectly vertical, so the column will visibly shift row-to-row during an ordinary drag — this is almost certainly what read as "jumping." Implementing goal-column snapping during a live drag would itself be a regression (it would stop the selection from following the pointer, which is what a drag-select is for). Nothing to fix here; flagging as context in case the user asks about it.
